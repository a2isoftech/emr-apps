## Repository state (`main_trimmed` branch)

This branch has been deliberately trimmed down from the full EMRApps monorepo to a minimal set of **8 packages** so that only the door access module can be built and run:

- `emr_one_door_access` — the only feature module kept
- `emr_one_shell_native`, `emr_one_shell_web` — the two shell apps (Android/iOS and web)
- `emr_one_core`, `emr_core_api`, `emr_one_theme`, `emr_one_localisations`, `emr_sharedtypes` — packages door_access and the shells transitively depend on

All other feature-module packages (accounts, CRM, EAM, ELV*, fire register, inform, inventory, prefs, security mgmt, stock take, tickets, transport, yard*, psnop, portal, etc.) have been deleted from `packages/`, and removed from the root `pubspec.yaml` `workspace:` list and from both shells' `dependencies`. The shells' `lib/main*.dart` and `lib/module_startup.dart` only wire up `DoorAccessRouteRegistry` now — do not re-add imports for the deleted modules.

**Known gap:** in `emr_one_shell_native`'s `main*.dart` files, the `doorAccessUrl` and `cameraStreamBaseUrl` endpoints are placeholders (`''`) for the `beta`/`prerelease`/`live` environments (only `dev` has real values, mirrored from web's `assets/environment_variables.json`). Fill these in with real backend/MediaMTX URLs before running those variants.

**Server-driven routing overrides local config:** if the logged-in user has the `permissions/menu-version-2/view` permission, `Startup._configureRouting` (in `emr_one_core/lib/startup.dart`) fetches a `"routing"` reference-data record from the Core API via GraphQL and builds the menu/tabs from that JSON instead of from `ModuleStartup.configure`. This is intentional and has **not** been disabled on this branch — it means the running app's menu can still show entries for deleted modules if the backend's `routing` reference data hasn't been updated to match. That's a backend data change, not something fixable in this repo.

## Commands

This is a Melos-managed Flutter monorepo (workspace config lives in the root `pubspec.yaml` under `melos:` and `workspace:`, not a separate `melos.yaml`).

```bash
# One-time setup
dart pub global activate melos
dart pub global activate mason_cli

# Authenticate against the private package feed (dartpackages.emrgroup.com) — required
# before any pub get, since emr_one_core depends on the hosted emr_flutter_theme package.
dart pub token add https://dartpackages.emrgroup.com

# Install deps + run codegen across the workspace (run this whenever switching branches)
melos fix

# Fetch deps only, from the repo root
flutter pub get

# Build all generated files (json_serializable / graphql_codegen etc.)
melos generate

# Run all tests + combined coverage
melos test
# or per-package: flutter test --no-pub  (run from inside a package dir)
# single test file: flutter test test/some_test.dart

# Lint
melos exec -- "dart analyze ."

# Localisation: edit packages/emr_one_localisations/l10n/*.arb, then:
melos l10n
```

`packages/**/lib/l10n/*.arb` is gitignored — those files are generated by copying from `packages/emr_one_localisations/l10n/*.arb` (see `melos.dart`'s `gen-l10n:copy-l10n-files`). If a fresh checkout fails `flutter pub get`/gen-l10n with a missing `app_en.arb` template error, run `melos l10n` (or `melos fix`) first.

### Running the shells

VS Code launch configs live in `.vscode/launch.json`, named e.g. `emr one web (dev)`, `emr one native (dev)`. Each `main_*.dart` entry point in the shells corresponds to an environment (`dev`, `beta`, `prerelease`, `live`/`main.dart`, plus web-only `local`, `alpha`, `apple`, `apple_test`).

Debug-mode Flutter web (DDC) can hit `net::ERR_INSUFFICIENT_RESOURCES` in Chrome on this codebase — `emr_one_core`'s dependency tree (notably `dlibphonenumber`'s generated per-locale geocoding data) compiles to thousands of individual JS modules in debug mode, exceeding Chrome's outstanding-request limit. Use a **release-mode** launch config (`"flutterMode": "release"`, e.g. `emr one web (dev - release mode)`) to verify web builds — release mode bundles via dart2js instead of DDC and avoids this entirely. Release mode has no hot reload/restart (no VM/incremental compiler attached); any code change requires a full stop and relaunch.

## Architecture

### Monorepo / package layout
Every package under `packages/` uses `resolution: workspace` and is listed in the root `pubspec.yaml`'s `workspace:` array. Feature-module packages depend on `emr_one_core` (and often `emr_core_api`, `emr_one_theme`, `emr_sharedtypes`) via `path:` deps. Note `emr_core_api` and `emr_one_core` have a **circular path dependency** on each other — this is intentional and works fine under pub's workspace resolution.

### Shell bootstrap flow
Both `emr_one_shell_native` and `emr_one_shell_web` follow the same pattern in `main*.dart`:
1. Load Firebase options + any JSON env overrides.
2. Call `Startup(...).start()` (from `emr_one_core/lib/startup.dart`), passing `appId`, per-environment `endpoints` map, and a `configureRouteRegistry` callback.
3. `Startup` initializes Firebase Remote Config, `AppConfig`, and — after login — calls `_configureRouting`, which either fetches server-driven routing JSON (see "Server-driven routing" above) or calls back into the shell's `configureRouteRegistry`.
4. Each shell's `configureRouteRegistry` either builds routes from server JSON via `RouteBuilder`/`EORouteConverter`, or falls back to the shell's own `module_startup.dart`, which calls `RouteRegistry.initRegistrationFunctions([...])` with each feature module's `XxxRouteRegistry.register` static method.

### Route registries and menus
Feature modules expose a `<Module>RouteRegistry` class (e.g. `DoorAccessRouteRegistry` in `emr_one_door_access/lib/routing/door_access_route_registry.dart`) with a `register` static method (adds `EORoute`s to the shared `RouteRegistry`) and a `widgetBuilders` map (used only by the JSON-driven routing path). `emr_one_core`'s `EoAppMenu` (side menu) and `HomeScreen` (dashboard tiles) both render purely from whatever routes are currently in `RouteRegistry` — there is no separate hardcoded tab/menu list in local code.

### emr_one_door_access structure
- `lib/routing/` — `DoorAccessRouteRegistry`
- `lib/screens/` — one folder per feature area (access_credentials, access_points, doors, door_controllers, floor_plans, groups, groups_access_points_link/delink, schedules, sites, users, alerts/*), each typically with a `*_screen.dart`, `*_data_source.dart` (grid data), and `*_filter_controller.dart`
- `lib/services/` — GraphQL/HTTP services per entity, plus `door_access_real_time.dart`/`signal_r_service.dart`/`signal_r_notification_bridge.dart` for SignalR-based live updates (endpoint key `doorAccessUrl`)
- `lib/models/`, `lib/extensions/`, `lib/widgets/` — shared data models, `BuildContext` extensions, and reusable widgets
- Heavily depends on `emr_one_core`'s barrel export (`package:emr_one_core/emr_one_core.dart`), which re-exports auth, config, data, networking, routing, screens, services, utilities, and widgets — check there first before assuming a symbol lives in `emr_one_door_access` itself.

### Floor plan camera live streaming
From a floor plan hotspot's popup menu (`_showHotspotMenu` in `lib/screens/floor_plans/floor_plan_editor.dart`), "Start Live Stream" appears whenever the hotspot's linked `AccessPoint.camera` is non-null — unlike "Unlock", it's shown even when the hotspot is `restricted`. It opens `LiveStreamDialog` (`lib/screens/floor_plans/widgets/_live_stream_dialog.dart`), which:
- Calls `FloorPlanController.startLiveStream`/`stopLiveStream` (→ `AccessPointsService.startCameraStream`/`stopCameraStream`, the `startCameraStream`/`stopCameraStream` GraphQL mutations) for a fixed 5-minute duration; "Reset duration" re-calls `startCameraStream` and restarts the countdown rather than extending it.
- Plays the stream via WHEP (WebRTC-HTTP Egress Protocol) against a MediaMTX-compatible server, using `lib/services/whep_client.dart` (`WhepClient`/`WhepSession`, ported from a POC at `C:\StreamingServerClient`) and `flutter_webrtc`'s `RTCVideoView`/`RTCVideoRenderer`. The playback URL is `<cameraStreamBaseUrl endpoint>/<Camera.streamPath>/whep`.
- Retries the initial WHEP connect up to 5 times (1s apart) before surfacing an error: the `startCameraStream` mutation reports `isRunning: true` as soon as the backend starts publishing to MediaMTX, but the RTSP→WHEP path isn't actually live for a brief moment after that, so an immediate negotiation can 404.
